# 每张表逐列填写说明

> 与 `00-完整性清单填写说明.md` 配合阅读。本文档说明四张表**每一列**的填写方式：填什么、为什么、
> 并附示例。用自然语言填写即可；英文代号如不便填写可先用中文，格式规范化由工程团队负责。

整件工作的目标：**帮助客户在下单时发现遗漏的物项，尤其是遗漏的对照。**
下面四张表，即为系统实现这一目标所需的全部信息。

---

## 本工作**不涉及**撰写实验步骤（protocol）

需澄清一个最易混淆之处：

- **实验步骤（protocol）** —— 即"如何完成该实验"（步骤一、步骤二……及所用材料）——
  这部分由系统从 protocols.io / 文献自动获取，**无需人工撰写**。
- **完整性清单（本工作的内容）** —— 即"一个**正确**的订单必须包含什么，尤其是哪些对照" ——
  这部分**在任何资料中都不存在**：一份 protocol 只记录其当时使用了什么，不会说明一个严谨的实验
  必须具备什么。那个差（被遗漏的对照）只存在于领域经验之中，**这才是本工作要提供的内容。**

因此本工作并非抄录步骤，也不是重复 protocols.io 已有的内容，而是提供其无法给出的那一层：
**该订单是否完整、是否正确。**

> 对于清单中"明显需要"的物品（膜、marker、封闭剂等），系统日后会从 protocols.io 自动填入。
> **当前先行手工填写，是为尽快打通流程、并作为校验系统的"标准答案"。** 因此这些明显项**一行一句、
> 不必纠结**，应将精力集中在**对照（controls）以及 `is_control` / `commonly_omitted` 两列** ——
> 那才是唯一依赖领域经验的部分。

---

## 一次下单的完整流程（四张表如何串联）

以"做一个 Western blot，检测蛋白 X"为例：

1. 系统先识别属于哪个**品类** → 使用 `categories.csv`
2. 下单前先询问几个**必答问题**（如目标分子量）→ 使用 `elicitation.csv`
3. 明确后，按该品类的**必需清单**生成购物车 → 使用 `checklist.csv`
4. 清单中每一项属于什么**角色**、是否为实验室常备（是否需过滤）→ 使用 `roles.csv`
5. 最后将"购物车中已有的"与"清单中必需的"对比，**差集即为遗漏项** → 向客户提示

填写的即为第 1–4 步的知识。第 5 步（提示）由系统自动完成，但其前提是这份清单已由领域专家填好。

## 表 1：`categories.csv` —— 选定要覆盖的实验品类

**作用：** 告知系统首发支持哪几种实验。选取 3–5 个最有把握、GarboBio 最常做的品类。

| 列 | 填什么 | 示例 |
|---|---|---|
| `category_id` | 品类的英文短代号，全小写、以下划线连接。不便用英文可先填中文，由工程团队规范化 | `western_blot` |
| `category_name` | 正式名称（中英文均可） | `Western blot / 蛋白免疫印迹` |
| `why_this_one` | 选择理由 —— 高频？GarboBio 常做？客户需求大？ | `GarboBio 每周都做，客户需求大` |
| `has_run_it` | 填写者是否亲手做过、是否有把握？yes / no。**仅将有把握的品类纳入清单** | `yes` |
| `notes` | 备注 | |

## 表 2：`roles.csv` —— 角色词典（所有品类共用一张）

**作用：** 定义"物品所承担的功能"。这是全系统共用的词典 —— checklist 中每个角色都须先在此表出现。
此表同时告知系统**哪些物品为实验室常备、无需推荐采购**（如水、枪头、手套），以避免购物车中出现冗余项。

**此表用时很短，快速完成即可** —— 重点是列出 checklist 中会用到的若干角色，并顺带标注哪些为
"实验室常备、无需采购"，无需追求穷举。

| 列 | 填什么 | 示例 |
|---|---|---|
| `role` | 角色的英文短代号（词典主键） | `loading_control` |
| `plain_description` | 用自然语言说明该角色的用途 | `上样对照抗体（管家蛋白）` |
| `lab_usually_owns_it` | 实验室是否通常已有？`yes` / `no` / `sometimes`。**标 yes 的系统不会推荐采购** | `no` |
| `always_buy_fresh` | 是否有效期短、每次需新购？yes / no | `no` |
| `notes` | 备注（如标注 `is_control=yes`） | |

> 提示：先将某个品类会用到的所有"物品功能"列出（如一抗、二抗、上样对照、封闭剂、膜、marker、
> 显影液、缓冲液、水、枪头等），常备项标 `yes`，需采购项标 `no`。此表填写一次，后续品类可大量复用。

## 表 3：`checklist.csv` —— ⭐ 核心：仅填写"最容易遗漏 / 最容易配错"的行

**作用：这是产品的护城河，也是唯一真正依赖领域判断的部分。**

**重要：此表无需从头罗列全部材料。** 明显需要的物品（膜、marker、封闭剂、缓冲液等）
由系统从 protocols.io 自动获取。仅需填写两类"资料中没有、依赖领域经验"的行：

1. **对照（controls）** —— 严谨实验必须具备、但客户经常遗漏的对照。
2. **最容易配错的规格** —— 明显需要的物品中，一旦配错整个实验即作废之处
   （如二抗宿主配错、磷酸化蛋白用错封闭剂）。

一个品类通常为 **3–6 行**。行数过多反而稀释重点。

| 列 | 填什么 | 示例 |
|---|---|---|
| `category_id` | 该行所属品类 | `western_blot` |
| `role` | 该项的角色（须为表 2 中已有的） | `loading_control` |
| `plain_name` | 通常的称呼 | `上样对照（anti-GAPDH）` |
| `required_or_optional` | `required`（必须）/ `optional`（推荐但可选） | `required` |
| `is_control` | 是否为**对照**？`yes` / `no` —— **最关键的列** | `yes` |
| `commonly_omitted` | 客户是否**经常遗漏**？`yes` / `no` —— **最关键的列** | `yes` |
| `why_required` | 一句话说明为何需要 / 配错的后果（该句会成为向客户的提示语） | `证明各泳道上样量一致，否则条带差异无法解读` |
| `spec_constraint` | 选用时最易出错的硬性规则（无则留空） | `管家蛋白，且分子量须与目标不同` |
| `depends_on` | 该行取决于哪项信息（对应表 4 的一个问题） | `target_protein_mw` |

> **判断规则很简单：**
> - 是对照吗？→ 填一行，`is_control = yes`。
> - 是"配错即作废、且客户常配错"的规格吗？→ 填一行，写清 `spec_constraint`。
> - 只是普通材料、配错也无妨？→ **无需填写，由系统自动获取。**
>
> `is_control` 与 `commonly_omitted` 均为 `yes` 的行是产品价值最高之处 —— 系统一旦发现购物车缺少该项，
> 即会重点提示客户。这条提示只有依赖领域经验才能写出，因为遗漏的内容在任何资料中都不存在。

## 表 4：`elicitation.csv` —— 下单前"必须先问清"的问题

**作用：这是"先理解、再推荐"的关口。**

**仅填写一类问题：答案会改变"采购内容"的问题。** 例如"一抗宿主是什么"会决定二抗、"是否为磷酸化蛋白"
会决定封闭剂 —— 这些需填写。而"需要跑多少样本""是否已有一抗"这类仅影响数量或流程、不改变必需项的
问题，**无需填写**，由系统另行处理。一个品类通常为 **3–5 个问题**。

| 列 | 填什么 | 示例 |
|---|---|---|
| `category_id` | 所属品类 | `western_blot` |
| `question` | 下单前向客户提出的问题，直接写成客户易懂的自然语言 | `目标蛋白的分子量大约多少 kDa？` |
| `required_before_recommending` | 未问清即不能推荐吗？`yes` = 必答项，未回答则系统暂不推荐（即关口） | `yes` |
| `what_it_changes` | 该答案会改变清单中的哪一行/哪个规格 | `决定上样对照须选不同分子量` |
| `answer_type` | 答案类型：`text`（文字）/ `number`（数字）/ `pick-list`（选择项） | `number` |
| `allowed_values` | 若为选择项，列出各选项，以分号分隔 | `rabbit;mouse;goat;rat;其他` |

> 如何找出这些问题：思考"同为 Western blot，因哪些差异会导致配置不同的物品？"
> 每一个"差异点"即对应一个需询问的问题。会改变必需项的 → `required_before_recommending = yes`。

## 填写前的顺序确认

1. 先填 `roles.csv`（建立词典）
2. 再填 `categories.csv`（选定品类）
3. 一次专注一个品类，将 `checklist.csv` 与 `elicitation.csv` 中同一 `category_id` 的行**一并填写**
4. 每完成一个品类先与工程团队核对，再进行下一个

任一列不确定如何填写时，可直接留空并在 `notes` 中写明疑问，后续一并讨论。

## 表 5：`troubleshooting.csv` —— 实验失败时"先查什么、再买什么"

**作用：** 客户说"我的 Western blot 没有条带"时，助手用这张表回答：最可能的原因是什么、
先检查什么、如果要买东西买哪一类。每一行 = 一个症状 + 一个原因。同一症状有三个原因就写三行。

**与 checklist 的关系：** 大多数失败都是清单里某一项缺了或配错了。这类行请在
`checklist_role_ref` 里指向对应的清单行（格式 `品类:角色`，如 `western_blot:secondary_antibody`）。

**当前状态：** 工程团队先起草了约 50 行（`confidence = drafted`），请您逐行审核。
审核无误就把 `confidence` 改成 `reviewed`，并填上 `reviewed_by` 和 `reviewed_on`。
不对的行直接删；缺的行直接加（`source` 填 `mary`）。**在您改成 reviewed 之前，助手会把这一行
说成"常见的可能原因"，而不是"Astor 的建议"。**

| 列 | 填什么 | 示例 |
|---|---|---|
| `entry_id` | 编号，`T` + 四位数字，工程团队分配，不要改 | `T0001` |
| `category_id` | 品类代号，须在 `categories.csv` 里 | `western_blot` |
| `symptom` | 客户会怎么描述这个现象，中英文用 ` / ` 隔开 | `完全没有条带 / no bands at all` |
| `likely_cause` | 这一行对应的**一个**原因 | `二抗宿主与一抗不匹配 / secondary does not match primary host` |
| `check_or_fix` | 具体先查什么、怎么改，越具体越好 | `确认二抗是 anti-[一抗宿主]；不匹配则更换` |
| `fix_role` | 修复需要的物品角色，须在 `roles.csv` 里；纯操作问题留空 | `secondary_antibody` |
| `buy_needed` | 通常要买东西吗？`yes` / `no` / `sometimes` | `yes` |
| `checklist_role_ref` | 对应的清单行 `品类:角色`；无则留空 | `western_blot:secondary_antibody` |
| `confidence` | `drafted`（未审）或 `reviewed`（已审） | `reviewed` |
| `source` | 内容来源：`checklist` / `mary` / `model` | `mary` |
| `reviewed_by` / `reviewed_on` | 审核人、日期（`reviewed` 时必填，`drafted` 时留空） | `Mary` / `2026-09-20` |
| `notes` | 备注 | |
